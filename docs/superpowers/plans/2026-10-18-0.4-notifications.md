# 0.4 Notifications Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Notification channels (Azure Communication Services, SMTP2GO, SMTP) that each get a chosen set of events – weekly digest, updates found, update failed/succeeded, check failing/recovered, user waiting for approval (and the layout-problems event, emitted from 0.5) – managed on the Settings page, with upgraded installs getting exactly the emails they got before.

**Architecture:** `app/notify/` holds a small provider interface (`send(config, message)`), three email providers, a channel store (one encrypted settings row), message rendering (one Jinja pair per event, sharing the digest look) and a `Notifier` that turns events into messages and sends them in the background. Existing code calls `app.state.notifier.<event>(...)` at the points where things happen; the notifier never raises into its caller.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, httpx (SMTP2GO API), stdlib `smtplib` run via `asyncio.to_thread`, `azure-communication-email` (existing), SQLite settings/meta.

**Spec:** `docs/superpowers/specs/2026-10-18-settings-auth-notifications-design.md` – section 3 (Notifications), release item 3. 0.2/0.3 code is on `main`.

## Global Constraints

- UK English; en dash (–), never em dash.
- Providers this round: `acs`, `smtp2go`, `smtp`. The interface must let chat/webhook providers (Teams Workflows, Slack, Discord, ntfy, Gotify, Pushover, Telegram, generic webhook, Apprise) be added later without touching event code – do **not** build them.
- SMTP2GO: `POST https://api.smtp2go.com/v3/email/send`, JSON body with `sender`, `to`, `subject`, `text_body`, `html_body`; API key in header `X-Smtp2go-Api-Key`; success when the response's `data.succeeded >= 1`.
- SMTP: host, port, security `starttls` | `tls` | `none`; `none` only when every address the host resolves to is private/loopback; optional username/password; sender. Presets: SMTP2GO `mail.smtp2go.com` port 587 starttls (2525 also listed in help), Microsoft 365 `smtp.office365.com` port 587 starttls. Timeout 20 s.
- Events (channel event keys) and defaults for a new channel:

| Key | When | Default on new channel |
|---|---|---|
| `digest` | weekly digest schedule / "Send digest now" | on |
| `updates_found` | a check finds updates not in the previous notification | off |
| `job_failed` | an update job fails (incl. rolled back) | on |
| `job_succeeded` | an update job succeeds | off |
| `check_failing` | 2 failed checks in a row, and once when it recovers | on |
| `layout_problems` | new layout problems (emitter arrives in 0.5) | on |
| `user_pending` | a new Microsoft user lands in "waiting for approval" | on |

- **Failed check** = the check raised, Docker couldn't be reached, or **every** registry lookup failed (≥ 1 checkable container and all of them ended in the error status). One image's error is not a failed check.
- **0.1/0.2 compatibility:** if `ACS_CONNECTION_STRING`, `DIGEST_FROM`, `DIGEST_TO` are set in env → a read-only channel "Email (from environment)" (provider `acs`) with events `{digest}` only. If they were saved on the 0.2 Settings page (database, not env) → migrated once into a normal editable channel "Email" with events `{digest}` only. Upgraded installs must get no new kinds of email unless an Admin turns them on.
- Secrets in channel config (`connection_string`, `api_key`, `password`) are stored encrypted (the whole channel list is one SecretBox-encrypted settings row `notification_channels`), never rendered back, never logged, never audited; blank on edit keeps the saved value.
- Provider errors shown in the UI or logged are fixed strings or the exception **type** only – provider messages can contain credentials.
- Sending never blocks or breaks the thing that triggered it (a job, a check, a sign-in): failures are caught and recorded per channel.
- Admin only for every notifications page and route; every change audited (kind `settings`).

## Review Focus

1. **Upgraded installs** (env email, DB-saved email, both, neither) – exactly one digest to the same recipients as before, nothing else; env wins over DB (no duplicate channel).
2. **A provider that hangs or errors** – the job/check/sign-in that triggered it finishes normally and promptly; the channel shows "Last attempt failed – <fixed reason>".
3. **"Updates found" repetition** – no repeat on the next check for the same update; a newer version for the same container is notified; an update that was fixed and later reappears is notified again.
4. **"Check failing"** – exactly one alert at the 2nd consecutive failure (not again at the 3rd), exactly one "recovered" afterwards; a single image's registry error never counts.
5. **Editing a channel** – saving the edit form with the secret left blank keeps it; switching provider clears the old provider's secrets; secrets never appear in the page, History or logs.

### Task 1: Providers

**Files:** Create `app/notify/__init__.py`, `app/notify/providers.py`, `tests/test_notify_providers.py`.

**Interfaces – Produces:**
- `@dataclass(frozen=True) class Message: subject: str; plain: str; html: str; recipients: tuple[str, ...]`
- `class NotifyError(Exception)` – `str(err)` is always one of the fixed reasons: `"The email service refused the login"`, `"The email service couldn't be reached"`, `"The email service rejected the message"`, `"The email service didn't answer in time"`, `"Unencrypted SMTP is only allowed to private addresses"`.
- `@dataclass(frozen=True) class ProviderField: name: str; label: str; kind: Literal["text","int","email","secret","choice"]; help: str = ""; required: bool = True; choices: tuple[tuple[str,str],...] = (); default: str = ""`
- `class Provider(Protocol): key: str; label: str; fields: tuple[ProviderField, ...]; def validate(self, config: dict) -> dict[str, str]; async def send(self, config: dict, message: Message, http: httpx.AsyncClient) -> None`
- `ACSProvider` (`key="acs"`, fields `connection_string` secret, `sender` email) – wraps the existing `EmailClient.from_connection_string(...).begin_send(...).result()` in `asyncio.to_thread`; a factory can be injected for tests.
- `SMTP2GOProvider` (`key="smtp2go"`, fields `api_key` secret, `sender` email) – exact API per Global Constraints; 401/403 → login refused; other 4xx or `succeeded < 1` → rejected; transport errors → couldn't be reached; timeout → didn't answer.
- `SMTPProvider` (`key="smtp"`, fields `host`, `port` int 1–65535, `security` choice starttls/tls/none, `username` optional, `password` secret optional, `sender` email) – `smtplib.SMTP`/`SMTP_SSL` in a thread, `ssl.create_default_context()`, 20 s timeout; `none` refused unless `all_private(host)`; `SMTPAuthenticationError` → login refused; `SMTPRecipientsRefused`/`SMTPDataError`/`SMTPSenderRefused` → rejected; `OSError`/`SMTPConnectError` → couldn't be reached; `socket.timeout` → didn't answer. Builds a `multipart/alternative` email with plain then HTML.
- `def all_private(host: str) -> bool` – every `getaddrinfo` address is private, loopback or link-local.
- `SMTP_PRESETS = {"smtp2go": {"host": "mail.smtp2go.com", "port": "587", "security": "starttls"}, "m365": {"host": "smtp.office365.com", "port": "587", "security": "starttls"}}`
- `PROVIDERS: dict[str, Provider]` keyed by `key`.

- [ ] **Step 1: Failing tests:** SMTP2GO with respx – exact URL, header, body fields; success; 401 → login refused; `succeeded: 0` → rejected; `httpx.ConnectError` → couldn't be reached; `httpx.ReadTimeout` → didn't answer; the API key never appears in `str(err)`. SMTP with a fake `smtplib.SMTP` class (monkeypatched) – starttls called for `starttls`, `SMTP_SSL` for `tls`, login only when username set, message has plain + HTML parts and the right recipients; `none` to `smtp.example.com` (monkeypatched `getaddrinfo` → public IP) refused before connecting; `none` to `10.0.0.5` allowed; auth error mapping. ACS with a fake factory – sender, recipients and both bodies passed; an exception → rejected. `validate` – missing required field, bad email, port out of range, unknown security.
- [ ] **Step 2–5:** FAIL → implement → PASS → full suite → commit "Notification providers: ACS, SMTP2GO, SMTP".

### Task 4: Notifier and event wiring

**Files:** Create `app/notify/notifier.py`, `tests/test_notifier.py`. Modify `app/main.py` (create notifier; job completion hook; "Send digest now"; check hook), `app/scheduler.py` (digest job when any channel subscribes to `digest`; scheduled check calls the hooks), `app/entra.py` (user_pending), `tests/test_scheduler.py`, `tests/test_routes.py`, `tests/test_entra.py`.

**Interfaces:**
- Consumes: Tasks 1–3.
- Produces – `class Notifier(store, channels: ChannelStore, settings_getter, http, providers=PROVIDERS, clock=...)`:
  - `async send(event: str, rendered: tuple[str,str,str] | None) -> int` – sends to `channels.subscribed(event)`, one `Message` per channel (that channel's recipients), each send wrapped in `asyncio.wait_for(..., 30)`; records per-channel result in meta `notify_last:<id>` as JSON `{"at": iso, "ok": bool, "reason": fixed string | null, "event": key}`; logs failures as `"Notification to <channel name> failed (<ExceptionType>)"`; never raises; returns the number sent OK.
  - `fire(event, rendered)` – schedule `send` as a background task (kept in `app.state.background`) so callers never wait.
  - `last_result(channel_id) -> dict | None`
  - `async digest(result) -> str` – "sent" | "skipped – nothing to report" | "skipped – no channel gets the digest" (used by the scheduled digest and "Send digest now", replacing `send_digest`).
  - `after_check(result: CheckResult | None, error: bool)` – called after every scheduled or manual check:
    - failed check rule from Global Constraints (`check_failed(result) -> bool` helper, exported); meta `check_failures` counter; at exactly 2 → fire `check_failing`; on a good check after an alert (meta `check_alerted`) → fire `check_recovered` once and reset.
    - updates found: `current_updates(result) -> dict[str, str]` mapping key → signature for every actionable item (newer build: key `"<container>:build"`, signature = remote digest; minor: `"<container>:minor"`, signature = tag; major: `"<container>:major"`, signature = tag; Mailcow: `"mailcow"`, signature = latest release). Previous map in meta `notified_updates`; new = keys whose signature differs or are absent; if any new and any channel subscribes → fire `updates_found` with the new items. Always store the current map (so fixed-then-reappearing items re-notify).
  - `job_finished(kind, target, status, user, job_id)` – fire `job_failed` or `job_succeeded`.
  - `user_pending(name, upn)` – fire.
  - `async test(channel_id) -> str | None` – sends `test_message` to that channel only, waits for it, returns None on success or the fixed reason.
- Wiring: `submit_job`'s wrapper in main.py calls `notifier.job_finished(...)` after the job's final status is known (read it from the store); `run_check` callers (scheduled check, Check now, dashboard first load) call `after_check`; `scheduled_digest` and `POST /digest/send` use `notifier.digest`; `reschedule`/`build_scheduler` add the digest job when `channels.subscribed("digest")` is non-empty (re-evaluated in `apply_settings` and after channel changes); `sign_in_entra` creates a pending user → `app.state.notifier.user_pending(...)` (pass a callback; don't import app state into entra.py).

- [ ] **Step 1: Failing tests:** a provider that raises → `send` returns 0, last result records the fixed reason, nothing propagates; a provider that hangs → returns within the timeout and the triggering job/route completes immediately (fire); failed-check rule (raised; docker error; all checkable containers errored → failed; one error among good ones → not failed; zero checkable containers → not failed); exactly one alert at the 2nd failure, none at the 3rd, one recovery; updates found: first check notifies, same result again doesn't, newer digest for the same container does, item removed then back does; job failed fires `job_failed` only to subscribed channels; digest job scheduled only when a channel subscribes; upgraded install with only the env channel → after a check with updates, a failed job and a pending user, **only** the digest is ever sent; `/digest/send` flash messages still work.
- [ ] **Step 2–5:** FAIL → implement → PASS → full suite → commit "Notifier and event wiring".
