# 0.3 Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Local accounts with a token-protected first start, two-step sign-in, Entra configured on the Settings page, Viewer / Operator / Admin roles with Entra mappings, Users and Account pages, a safe upgrade from 0.1/0.2, a `reset-admin` command and a public `/healthz`.

**Architecture:** A `users` table (migration 3) owns identities; the server-side session (0.2) now carries only `user_id` + CSRF, and the auth guard loads the user from the database on **every** request, so disable / role change / sign-out-everywhere take effect at once. Roles are an ordered enum checked by a `require_role(...)` dependency on each route. Entra's OAuth client is built from the effective settings and rebuilt by `apply_settings`. First start, upgrade detection and the 0.1 allow-rule migration run once at startup, recorded in `meta`.

**Tech Stack:** Python 3.12, FastAPI, Jinja2, SQLite, authlib (existing), `argon2-cffi`, `pyotp`, `segno` (QR as inline SVG, pure Python). New data file `app/data/common-passwords.txt` (SecLists `10k-most-common.txt`, MIT – owner approved the download).

**Spec:** `docs/superpowers/specs/2026-10-18-settings-auth-notifications-design.md` – section 2 (Accounts and sign-in, incl. "Health endpoint"), release item 2. Earlier 0.2 code is on `main`.

## Global Constraints

- UK English in UI, emails, docs. En dash (–), never em dash.
- Roles: `pending` (no access, "waiting for approval"), `viewer`, `operator`, `admin`, ordered pending < viewer < operator < admin.
- Role permissions: **Viewer** – dashboard, History list of update jobs **without logs**, own Account page. **Operator** – Viewer + Check now, all container/project/version updates and previews, job logs and live log streams. **Admin** – Operator + Settings, Users, History "Changes" (audit), Send digest now, Mailcow update, dashboard self-update.
- Default role for new SSO users: setting `default_role` ∈ {`pending`, `viewer` (default), `operator`}, plus the one-off migration value `admin_legacy`, shown as "Admin (as in 0.1)" and removed from the choices once changed. Never plain `admin`.
- Entra app role names: `DockerManager.Admin`, `DockerManager.Operator`, `DockerManager.Viewer`.
- Role from mappings: **highest** of all matching sources (app roles, group mappings); none → default role. Applied at every Entra sign-in only to **unpinned** users. Any role an Admin sets by hand (approve, change role) and every role created by the 0.1 migration is **pinned**.
- There must always be ≥ 1 active (not disabled) Admin: refuse demote/disable/delete of the last one, and never let a mapping recompute demote the last one.
- Passwords: argon2id via `argon2-cffi` defaults, minimum **12** characters, no composition rules, rejected if (case-insensitively) in `app/data/common-passwords.txt`.
- Rate limits: **5** failures per account key (lower-cased email, whether or not the account exists) per **15** min → that key locked for **15** min; **20** failures per IP per **15** min → IP blocked for **15** min. Same response for unknown account and wrong password; locked/blocked shows "Too many attempts – try again in 15 minutes."
- Two-step sign-in: TOTP (pyotp, 30 s, 6 digits, valid_window=1, a used time-step can't be reused), **10** single-use recovery codes stored as SHA-256 hashes. Setting `require_totp_admins` default **on**, applies to **local** accounts only.
- Invites valid **72** hours; one-time passwords force a change at next sign-in.
- Setup token: 32 bytes `secrets.token_urlsafe`, file `<DATA_DIR>/setup-token` mode `0600`, logged once at startup; same rate limits as passwords (by IP).
- Public paths (no sign-in): `/auth/*`, `/static/*`, `/healthz`, and `/setup*` **only while setup is open**. Everything else needs a signed-in, enabled, non-pending user.
- Secrets (client secret, TOTP secrets) encrypted with the 0.2 `SecretBox`; never rendered, logged or written to History.
- Existing installs (0.1 or 0.2 databases) must keep working with no compose/`.env` change and must never be sent to the setup token.
- Match existing code style (module docstrings, sparse why-comments, plain functions).

## Review Focus

1. **Last Admin** – demote, disable, delete or a sign-in mapping recompute that would leave no active Admin is refused (UI shows why; sign-in keeps Admin and logs a warning).
2. **Upgrade from 0.1/0.2** with `AZURE_*` env, with and without `ALLOWED_EMAILS` / `ALLOWED_GROUP_ID` – no setup token, owner still gets in as Admin, migration runs exactly once (restart doesn't redo it), and env `ALLOWED_*` are ignored afterwards.
3. **Already signed-in session after disable / role change / sign-out-everywhere** – the very next request is refused or gets the new permissions.
4. **Unknown email vs wrong password** – identical status, message and roughly equal work (hash a dummy); failures for unknown emails still count towards that key's lock.
5. **Setup race and replay** – two concurrent setup submissions create one admin; after setup `/setup` is 404, the token file is gone and the old token does nothing.
